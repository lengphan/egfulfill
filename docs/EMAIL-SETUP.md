# Transactional email — how it works, and how to change it

Written after getting it working for the first time on 2026-07-22. Until that date **no
email had ever been sent by this system**, and nothing said so — which is the first thing
to understand about this subsystem.

---

## 1. The one rule

**`sendMail()` never throws.** Every caller treats a total mail outage as success, so a
seller clicking "forgot password" sees the same friendly message whether a link went out or
nothing happened at all.

That is deliberate — a broken mailer must not fail a password reset request — but it means
**mail failure is invisible from inside the app.** The only way to know is to ask:

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.egful.store/api/admin/mail-diag | jq
```

Admin-only. Reports which transport is configured and, usefully, what each feature silently
does when mail is off. Add `?to=you@real-address.com` to actually send.

## 2. Only the HTTP API works, and it always will be

**DigitalOcean blocks outbound SMTP (ports 25/465/587) on droplets.** `SMTP_HOST` will
always time out. The `SMTP_*` variables in `.env` are correct and permanently unusable —
leave them, don't debug them.

Everything goes over **HTTPS:443** via the provider's HTTP API. Any provider you pick must
have one; an SMTP-only provider cannot work on this host.

## 3. `ok: true` is not "delivered"

The API returns success on **acceptance**. The provider can still refuse to send afterwards
— which is exactly what happened here: `ok: true`, empty inbox, and the real answer only in
**Brevo → Transactional → Logs**.

Always finish by reading the provider's own log. `Sent` is not `Delivered`.

## Changing the sending domain

Say `egful.store` becomes `example.com`.

### 1. Authenticate the DOMAIN, never a single address

Brevo → **Senders, Domains & Dedicated IPs → Domains → Add a domain**.

Do **not** take the "verify this email address" option. It sends a confirmation link to the
address itself, and `no-reply@` has no mailbox to receive it. That route cannot complete.

### 2. Add the DNS records

DNS for `egful.store` is at **Namecheap** (`dns1.registrar-servers.com`) → Domain List →
Manage → **Advanced DNS**.

| Type | Host | Value |
|---|---|---|
| TXT | `@` | `brevo-code:…` (ownership) |
| TXT | `brevo._domainkey` | the long DKIM string |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:you@example.com` |

**Host field takes the prefix only.** Namecheap appends the domain itself — typing
`brevo._domainkey.example.com` produces `brevo._domainkey.example.com.example.com`, which
resolves to nothing. This is the single most common failure.

**Namecheap has two save steps.** The green ✓ commits a row to the form; **SAVE ALL
CHANGES** at the top of Host Records is what actually writes it. Stopping after the ✓ looks
like success and saves nothing.

### 3. SPF — edit, never add

There is already an SPF record, generated by Namecheap's Email Forwarding:

```
v=spf1 include:spf.efwd.registrar-servers.com ~all
```

**Edit that row** to append the provider:

```
v=spf1 include:spf.efwd.registrar-servers.com include:spf.brevo.com ~all
```

**Two `v=spf1` records make SPF fail entirely** — worse than having none. If the record
isn't editable in Host Records, it's coming from the **MAIL SETTINGS** section further down
the same page; either keep forwarding and leave SPF alone (DKIM alone still delivers), or
switch Mail Settings off and write your own single record.

### 4. Point the app at the new address

```
SMTP_FROM=EGFULFILL <no-reply@example.com>
```

Then **`docker compose up -d api`** — see the trap below.

### 5. Verify

```bash
dig +short TXT brevo._domainkey.example.com @8.8.8.8      # the DKIM value
dig +short TXT example.com @8.8.8.8 | grep -c v=spf1       # must be exactly 1
dig +short TXT _dmarc.example.com @8.8.8.8
```

If a public resolver looks stale, ask the authoritative server directly — that bypasses
caching and tells you what is really published:

```bash
dig +short TXT example.com @dns1.registrar-servers.com
```

Then press **Verify** in the provider, send a test, and read their log for **Delivered**.

## Changing the mail provider

`src/mailer.js` is the only file that talks to a provider. It tries the HTTP API first and
falls back to SMTP, which on this host never succeeds.

To swap providers (Postmark, Resend, SendGrid, SES):

1. Confirm they offer an **HTTP send API**. SMTP-only is unusable here.
2. Add the new branch in `mailer.js` alongside the Brevo one — same shape: read the key at
   **call time**, not module load. A module-level `const KEY = process.env.X` snapshots at
   boot, so a key saved later never applies (CLAUDE.md §3).
3. Update `mailConfigured()` and the `transport` field in `/api/admin/mail-diag`, or the
   diagnostic will report the old provider and mislead whoever is debugging.
4. Redo the DNS above with the new provider's DKIM/SPF values. **They are not portable** —
   each provider signs with its own key.
5. Keep the old provider's records until the new one is verified, then remove them. An
   orphaned DKIM record is harmless; a missing one during cutover is an outage.

## Traps that have already cost time

**API key vs SMTP key.** Brevo issues both on the same screen and they are *not*
interchangeable: `xkeysib-…` is the API key, `xsmtpsib-…` is the SMTP password. They are
generated independently and **never share a body**. Editing the prefix of one to make the
other produces a key that exists nowhere, and Brevo answers `401 {"message":"Key not
found"}` — which reads like a permissions problem and isn't.

**`docker compose restart` does not reload `.env`.** It restarts the process inside the
existing container, keeping the environment it was *created* with. Use
`docker compose up -d api`. Confirm with:

```bash
docker compose exec api printenv BREVO_API_KEY | cut -c1-24
```

**Test with a real inbox.** `you@example.com` fails even with a perfect setup, and you end
up debugging the wrong layer.

**First send often lands in spam.** A domain with no sending history gets one sceptical
look from Gmail. Mark it "not spam" once.

---

## Known gap

**Signup sends no email at all** — key or no key, domain or no domain. That is unbuilt, not
misconfigured. Password reset, team invites and top-up alerts all work once the above is
done; signup will not, and no amount of DNS fixes it.
